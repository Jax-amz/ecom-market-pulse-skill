# 跨境资讯月报技术方案

> 版本：1.1  
> 时区：`Asia/Shanghai`  
> 归档周期：自然月  
> 业务截止：每月最后一个自然日 `16:00`  
> 正式输出：通过最终关门验证的 `monthly/YYYY-MM.json`

## 1. 目标

月报用于在月末当天完成经营复盘，让用户不必等到下月才看到结果。它把目标月工作日日报与月末截止增量事实重新聚类，提炼平台变化、成本风险、流量转化、经营机会和下月关键日期。

月报不是日报或周报正文拼接，也不是“最近 30 天”滚动摘要。日期归档仍是自然月，但资讯统计使用月末 16:00 业务截止点。

## 2. 周期合同

定时任务在每月最后一个自然日运行，不能写死为 31 日。二月以及只有 30 天的月份同样必须触发。

以 2026 年 7 月为例：

- `date = 2026-07-01`
- `period.month = 2026-07`
- `period.startDate = 2026-07-01`
- `period.endDate = 2026-07-31`
- `windowStart = 2026-07-01T00:00:00+08:00`
- `windowEnd = 2026-07-31T16:00:00+08:00`
- `build.dataCutoffAt = windowEnd`
- 文件名为 `monthly/2026-07.json`

`generatedAt` 和 `gate.validatedAt` 都不得早于 `windowEnd`。16:00 前可以准备 `pending` 草稿，但到达截止点后必须完成增量采集并重新生成。

## 3. 输入日报与月末截止增量

第一版按目标月周一至周五计算预期日报，不接入法定节假日和调休日历。2026 年 7 月共有 23 个预期工作日。

每份输入日报必须同时满足：

1. 日期属于目标自然月且为周一至周五。
2. 存在于本地 `runtime/exports/manifest.json` 的 `reports.daily`。
3. 固定路径为 `daily/YYYY-MM-DD.json`，不使用 `latest.json`。
4. `reportType = "daily"`。
5. `gate.status = "passed"` 且 `gate.issues = []`。
6. 报告日期、manifest 日期和文件名一致。

任一预期日报缺失时，先按日期补跑；不得用周末、其他日期或周报替代。

月末最后一天 16:00 必须再执行一次增量采集：

- 月末为工作日：若发现上午日报之后的新文章，完成分析并重建当天日报。
- 月末为周末：不虚构周末日报；截止采集新增的合格文章直接进入月报候选事实层。
- 截止点之后首次发现的资讯归入下一个业务月，不能丢弃，也不能回写已发布月报。

## 4. 聚合边界

月报候选集由以下两部分取并集：

1. 目标月全部合格日报的 `sections[].items[].articleId`。
2. 月末截止增量采集在 `windowEnd` 前确认的合格文章。

所有候选都必须根据 `articleId` 回到 DuckDB 文章事实层和分析记录。

确定性程序负责：

- 日期窗口、月末日期和工作日集合。
- 日报完整性与截止增量检查。
- `articleId` 回查。
- 同事件跨日聚类和代表文章选择。
- 来源与分类统计。
- 扩展字段引用校验。
- JSON Schema 校验和稳定文件名。

Codex 主 Agent 负责：

- 本月核心经营判断。
- 六个平台变化矩阵。
- 成本风险、流量转化和机会提炼。
- 有文章证据的月度趋势。
- 下一自然月的关键生效日和截止日。
- 完整报告的最终关门判断。

不得只基于周报生成月报。周报已经进行过一次筛选，二次提炼会放大遗漏并削弱原始证据链。

## 5. 输出合同

月报沿用日报、周报共享字段，并增加：

- `period`
- `monthLead`
- `platformMatrix`
- `costAndRisk`
- `trafficAndConversion`
- `opportunities`
- `trendEvidence`
- `nextMonthCalendar`

`platformMatrix` 固定按以下顺序输出：

1. Amazon
2. Walmart
3. Shopify
4. TikTok Shop
5. Temu
6. eBay

`stats.dailyReports` 是目标月已通过关门的工作日日报数量。正式月报必须等于该月预期工作日数量；月末周末增量不增加日报数量。

## 6. 引用完整性

以下字段的 `articleIds` 必须存在于同一月报的 `sections[].items[].articleId`：

- `platformMatrix`
- `costAndRisk`
- `trafficAndConversion`
- `opportunities`
- `trendEvidence`
- `nextMonthCalendar`

每个 `trendEvidence.eventCount` 必须等于对应 `articleIds` 去重后的数量。`nextMonthCalendar.date` 必须位于紧随报告期之后的自然月。

## 7. 最终关门

只有全部满足时才允许 `gate.status = "passed"`：

1. 已到达月末当天 16:00。
2. 截止增量采集已经完成。
3. `generatedAt >= windowEnd` 且 `gate.validatedAt >= windowEnd`。
4. 全部预期工作日日报齐全且关门通过。
5. 候选文章均能回查 DuckDB 事实和来源 URL。
6. 跨日重复事件已经聚类。
7. 月度结论与趋势均有入选文章支撑。
8. 扩展字段引用合法。
9. `trendEvidence.eventCount` 与证据数一致。
10. 报告通过 Pydantic 合同和 JSON Schema。

`pending` 和 `rejected` 月报只保留在本地审计链路，不得导出或发布。

## 8. 导出与发布

本地稳定路径：

```text
runtime/exports/monthly/YYYY-MM.json
runtime/exports/monthly/latest.json
```

公开白名单：

```text
monthly/YYYY-MM.json
manifest.json
```

发布顺序固定为：

1. 校验本地报告 `gate.status = passed`。
2. 上传月报稳定文件。
3. 校验本地、服务器文件和公开 URL 的 SHA-256。
4. 将目标月条目写入 `manifest.reports.monthly`，按日期倒序。
5. 最后原子替换 `manifest.json`。
6. 浏览器验证真实页面。

不得公开 DuckDB、原始响应、正文缓存、运行日志、模型审计、附件、配置或密钥。

## 9. 调度

月报业务截止为每月最后一个自然日 16:00，正式定时任务安排在当天 20:00。预留四小时用于截止补采、分析、日报刷新、月度聚类与关门。

月末恰逢周五时：

1. 16:00 先执行周报任务。
2. 周报发布后保留最新 manifest。
3. 20:00 再执行月报任务。
4. 月报更新 manifest 前必须重新读取远端最新版本，保留当天刚发布的周报条目。

重跑同一月份时保持 `monthly/YYYY-MM.json` 稳定路径不变；新 revision 只有通过关门和哈希验证后才能替换旧版本。

## 10. 验收标准

- 任意输入日期都能归一到目标自然月月初。
- 二月、30 天月份、31 天月份和跨年月份的月末 16:00 截止正确。
- 只要求周一至周五日报。
- 月末周末增量不虚构日报。
- 缺失任一预期日报时拒绝关门。
- 截止增量没有完成时拒绝关门。
- `generatedAt` 或 `gate.validatedAt` 早于 16:00 截止时拒绝关门。
- 月报直接基于日报与截止增量文章事实层聚合。
- 六个平台矩阵顺序固定。
- 所有月度扩展引用可回溯。
- `stats.dailyReports` 与预期工作日数量一致。
- 仅 `gate.status = "passed"` 的报告可导出。
- 文件名稳定为 `monthly/YYYY-MM.json`。
- 发布严格执行报告先上传、manifest 最后更新。
