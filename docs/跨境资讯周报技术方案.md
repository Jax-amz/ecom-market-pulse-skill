# 跨境资讯周报技术方案

> 文档状态：实施方案 v2
> 适用项目：`ecom-market-pulse-skill`
> 业务时区：`Asia/Shanghai`
> 周报口径：本周周一至周五 5 个业务日期，周五 `16:00` 截止
> 正式输出：通过最终关门验证的 `weekly/YYYY-Www.json`

## 1. 目标

在现有跨境资讯日报链路之上，生成一份可审计、可追溯、可发布的跨境资讯周报。

周报不是 5 份日报的简单拼接。它以目标工作周内已经通过关门的 5 份日报为基础，在周五 16:00 先执行截止增量采集并刷新周五日报，再回到 DuckDB 补齐原文、分析、证据和冲突信息，完成跨日事件去重、主题归纳、重要变化提炼和下周观察。

周报应回答五个问题：

1. 本周真正值得经营团队同步的变化是什么。
2. 哪些政策、费用、物流、流量或合规变化已经被可靠证据确认。
3. 哪些事件在多个工作日重复出现，可能形成持续信号。
4. 哪些内容只是同一事件的重复报道，不应再次占用阅读篇幅。
5. 下周有哪些生效日期、截止日期或需要继续核实的事项。

## 2. 已确认的业务口径

### 2.1 周报周期

每期周报处理本周周一至周五生成的 5 份日报。周五 16:00 是业务截止点；周六、周日没有日报，也不参与完整性检查。

页面归档不展示 ISO 周和时间窗口，只显示周序与标题；正文标题下方单独显示周一至周五日期范围：

```text
2026 年 7 月
第3周    周报标题
第2周    周报标题
第1周    周报标题

2026-07-20 ～ 2026-07-24
```

“第 N 周”根据该期周一在当月的位置计算：

- 1～7 日：第 1 周
- 8～14 日：第 2 周
- 15～21 日：第 3 周
- 22～28 日：第 4 周
- 29 日以后：第 5 周

跨月的一周归到周一所在月份。第一版中的工作日固定指周一至周五，暂不引入法定节假日和调休日历。

### 2.2 文件名与页面展示分离

周报文件继续使用：

```text
weekly/YYYY-Www.json
```

`YYYY-Www` 只用于程序内部计算、文件唯一命名和防止重复发布，不在页面上展示。

定时任务在周五 16:00 生成本周周报。手动执行时默认选择最近一个已经到达周五 16:00 截止点的工作周，不生成任意时刻向前滚动 120 小时或 168 小时的报告。历史补报必须显式指定目标 `YYYY-Www`。

### 2.3 不允许替代

不得使用以下内容替代目标工作周：

- 尚未到达周五 16:00 截止点的工作周。
- `latest.json` 指向的其他周报。
- 其他日期的日报。
- 本地存在但没有进入公开 manifest 的日报。
- `gate.status != "passed"` 的日报。
- 日期字段与目标业务日期不一致的日报。
- DuckDB 中已分析但没有进入已发布日报的文章。

## 3. 设计原则

- **日报与截止补采决定入选边界**：周报候选文章来自目标 5 份有效日报；周五 16:00 补采发现新文章时先刷新周五日报。
- **DuckDB 提供完整证据**：日报确定 articleId 后，再从 DuckDB 读取文章、分析、证据、冲突和运行追溯信息。
- **候选集与展示集分离**：全部候选事件用于统计和趋势判断，周报正文只展示提炼后的重点事件。
- **跨日重新聚类**：日级去重结果不能直接代替周级去重，需要识别跨日重复报道、事件后续进展和多日信号。
- **Agent 只能在候选集内归纳**：不得新增不存在的文章、事实、日期和引用。
- **程序负责硬约束**：周期、5 份日报覆盖、候选 articleId、引用校验、数量、文件名、哈希和发布顺序由程序确定。
- **先关门、后导出**：`gate.status != "passed"` 或 `gate.issues` 非空的报告不得导出和发布。
- **业务截止不留缺口**：周五 16:00 之后及周末首次发现的资讯进入下一业务周首个合格日报，不回写已发布周报。
- **JSON 优先**：正式交付物为 JSON；Markdown 仅作为可选阅读副本。
- **保持轻量**：继续复用现有六张核心表，不新增周报专用表，不引入工作流平台。

## 4. 当前能力与真实实施边界

### 4.1 已具备的基础能力

现有代码已经具备：

- `weekly` 报告类型和 Pydantic/JSON Schema 基础合同。
- ISO 周编号和周报文件命名能力。
- 十个固定分类区块。
- `period`、`themes`、`recurringSignals`、`importantChanges`、`nextWeekWatchlist` 字段结构。
- `sourceDirectory` 基础结构。
- 报告级关门结果字段。
- 仅允许 `gate.status = "passed"` 的报告进入导出器。
- 原子写入周报 JSON 的基础能力。

### 4.2 尚未具备、必须补齐的能力

以下能力当前不能视为已经完成：

1. 目标工作周和 5 个预期业务日期的统一计算。
2. 5 份已发布日报的完整性检查。
3. 从 manifest 和日报 JSON 构建候选 articleId 集合。
4. 按 articleId 回查 DuckDB 完整证据。
5. 不依赖发布日期的跨日事件聚类。
6. 候选集到重点展示集的提炼。
7. 真实的重复信号、重要变化和下周观察生成。
8. 所有周报叙事字段的 articleId 引用校验。
9. `gate.status = "passed"` 时强制 `issues = []`。
10. 关门合并后再次执行完整 Pydantic/JSON Schema 校验。
11. manifest 生成、发布白名单、远端上传和公网验证。
12. 博客页面对 `recurringSignals`、`importantChanges` 的展示和报告状态防御校验。

当前稳定 CLI 仍只有：

```text
validate-config
collect
schema-check
```

面向业务的推荐入口继续是 Codex Skill 和 Scheduled 任务。Python 模块作为实现基础、CI 和诊断工具，不要求用户手动拼接完整流程。

## 5. 输入数据

周报输入分为五层。

### 5.1 目标工作周

编排层根据 `Asia/Shanghai` 当前日期计算：

- 周一至周五 5 个业务日期。
- 周五 `16:00:00+08:00` 业务截止点。
- 周报归档日期，固定为该周周一。
- 内部文件名 `YYYY-Www.json`。
- 页面显示的月份、“第 N 周”和周一至周五日期范围。

“第 N 周”不是 ISO 周号，也不按已发布周报数量编号。以周一 `period.startDate` 在所属月份的位置计算：`N = ((day - 1) // 7) + 1`。例如 `2026-07-06`、`2026-07-13`、`2026-07-20` 分别是 7 月第1、2、3周；`2026-06-29` 是 6 月第5周。正文日期范围固定使用 `period.startDate ～ period.endDate`。

每次执行的最终交付必须简洁输出：

```text
归档：第X周
日期范围：YYYY-MM-DD ～ YYYY-MM-DD
```

### 5.2 已发布日报清单

目标日期中的每一份日报必须同时满足：

1. 存在于本地 `runtime/exports/manifest.json` 的 `reports.daily`。
2. manifest 条目的 `date` 等于目标日期。
3. manifest URL 指向固定的 `daily/YYYY-MM-DD.json`。
4. 本地对应 JSON 存在。
5. JSON 的 `reportType = "daily"`。
6. JSON 的 `date` 等于目标日期。
7. JSON 的 `gate.status = "passed"`。
8. JSON 的 `gate.issues` 为空。
9. 公网 URL 可访问且内容与本地发布版本一致。

只有同时满足以上条件的日报，才算目标周的一份有效日报。

在使用周五日报前必须执行截止增量采集。若发现上午日报生成后的新文章，完成分析并重新生成、关门和发布周五日报；不能因为上午版本已经 `passed` 就直接汇总。

### 5.3 候选 articleId

从 5 份有效日报的以下路径提取 articleId：

```text
sections[].items[].articleId
```

处理规则：

- 合并 5 份日报的 articleId。
- 对完全相同的 articleId 去重。
- 记录每个 articleId 首次和最后出现的业务日期。
- 记录它出现在哪些日报中。
- 不接收日报以外的新 articleId。

### 5.4 DuckDB 证据回查

按候选 articleId 回查以下内容：

- `articleId`
- `eventKey`
- `sourceId`、`sourceName`、`sourceClass`
- `sourceUrl`
- `originalTitle`
- `publishedAt`
- `primaryCategory`
- `impactDimensions`
- `whatHappened`
- `whyImportant`
- `suggestions`
- `effectiveAt`、`deadlineAt`
- `evidence`
- `corroboratingSources`
- `conflicts`
- 分析 Prompt、执行器和分析时间
- 所属日报日期

任一候选 articleId 无法在 DuckDB 中还原完整证据时，周报必须拒绝，不得只使用日报中的简化文本继续生成。

### 5.5 信源目录快照

周报 `sourceDirectory` 不直接使用周一执行时的当前配置覆盖历史事实，而是合并 5 份日报中的 `sourceDirectory`：

- 取 5 份日报中出现过的全部信源。
- 同一信源元数据一致时合并。
- 元数据不一致时优先使用时间最新日报中的名称和主页，同时把差异写入构建诊断。
- `articleCount` 重新按周报最终展示集统计。
- 0 篇信源仍保留。

## 6. 5 份日报完整性关门

### 6.1 通过条件

目标工作周必须满足：

- `expectedDailyReports = 5`
- `passedDailyReports = 5`
- `missingDates = []`
- `invalidDates = []`

`stats.dailyReports` 固定为实际通过检查的日报数量，正式发布的周报必须等于 5。

### 6.2 缺失日报处理

发现缺失或无效日报时：

1. 明确列出缺失日期或失败原因。
2. 对该业务日期执行对应日报的完整补跑。
3. 补跑仍必须完成采集、分析、日报构建、最终关门、JSON 导出和日报发布。
4. 不得用相邻日期、历史日报或 `latest.json` 替代。
5. 无法补齐 5 份有效日报时，周报关门必须拒绝。

周六、周日不属于预期日报，不得因为周末没有日报而拒绝周报。

## 7. 周度跨日去重与事件关系

### 7.1 为什么不能直接复用日级 eventKey

现有日级 `eventKey` 包含发布时间信息，适合日报内去重，但同一事件在不同日期被重复报道时可能得到不同键。周报必须增加不依赖日报日期的周度聚类步骤。

### 7.2 周度聚类结果

每组候选文章必须归入以下关系之一：

- `same-event`：同一事实的重复报道，只保留一个周报代表事件。
- `follow-up`：同一事件在后续工作日出现实质新进展，保留时间线关系。
- `recurring-signal`：同类异常或讨论在至少两个不同工作日重复出现，但不是同一篇转载。
- `independent`：独立事件。

### 7.3 代表文章选择

`same-event` 组只在周报 `sections` 中展示一个代表文章，优先级：

1. 官方信源。
2. 具有更直接原文证据的专业媒体。
3. 社区来源。
4. 聚合来源。
5. 同级别中选择信息更完整、时间更新且冲突更少的文章。

其他文章作为佐证保留在 DuckDB 和关门证据包中，不重复展示。

### 7.4 重复信号判定

`recurringSignals` 只有满足以下条件才能生成：

- 至少涉及两个不同工作日。
- 至少有两个不同 articleId。
- 不是同一原文的转载复制。
- summary 明确说明是“重复信号”或“待观察现象”，不得写成官方确认事实。
- 所有 articleId 都存在于周报最终展示集。

仅仅属于 `seller-community-signal` 分类，不代表自动构成重复信号。

## 8. 候选集与重点展示集

### 8.1 候选集

候选集由 5 份日报 articleId 合并并完成周度聚类后得到，用于：

- `stats.uniqueEvents`
- 周度主题判断
- 多日信号判断
- 重要变化候选
- 下周关键日期候选
- 构建追溯

### 8.2 重点展示集

周报正文不是候选集的完整复制。主 Agent 只能从候选集中选择重点展示事件，程序负责校验选择结果。

第一版建议：

- 总展示事件默认 12～20 个。
- 候选事件不足 12 个时全部展示，不补写内容。
- 超过 20 个时必须提炼，不得继续全部铺开。
- 只要 5 份日报候选集中某个固定分类非空，周报对应分类就必须至少保留 1 个真实候选事件。
- 分类代表事件仍按重要性选择，不得为满足覆盖要求补写候选集之外的内容。
- 同一事件只展示一次。

优先展示：

1. 已确认的官方政策、规则和费用变化。
2. 具有明确生效日或截止日的事项。
3. 影响钱、货、号、流量、效率、竞争中多个维度的事件。
4. 多个工作日重复出现的真实信号。
5. 存在来源冲突、可能误导经营判断的高风险事件。
6. 对主要跨境平台或市场产生实质影响的变化。

全部展示事件继续进入十个固定分类区块；空分类保留空数组。

## 9. Agent 周报归纳

主 Agent 接收：

- 确定性的候选事件集合。
- 周度聚类关系。
- 推荐的重点展示候选。
- 每篇文章的结构化分析和证据。
- 5 份日报覆盖结果。

主 Agent 输出：

- `lead`
- 重点展示 articleId
- `themes`
- `recurringSignals`
- `importantChanges`
- `nextWeekWatchlist`

### 9.1 Lead

`lead.title` 必须使用本周最值得关注的具体变化或主题，不得使用：

- 跨境电商资讯周报
- 本周跨境经营主线
- 本周经营变化汇总
- 风险与机会并存

`lead.summary` 应说明本周变化之间的经营关系，不能只是统计数字或分类列表。

### 9.2 Themes

- 主题数量建议 3～6 个，合同上限仍为 8 个。
- 每个主题至少引用一个最终展示 articleId。
- 主题不得只有分类名称。
- 主题之间不得重复表达同一变化。
- 所有趋势表述必须能由事件、日期和来源证据支持。

### 9.3 ImportantChanges

`importantChanges` 只收录已经确认的：

- 官方政策。
- 平台规则。
- 费用和税务变化。
- 履约限制。
- 合规要求。
- 明确生效或截止事项。

非官方消息只有在得到可靠原始来源或多源佐证后才能进入；否则应放在重复信号或待观察事项中。

### 9.4 NextWeekWatchlist

`nextWeekWatchlist` 可以收录：

- 下一 ISO 周生效的政策、费用和功能。
- 下一 ISO 周截止的申报、合规或活动事项。
- 本周已有证据、下周需要继续验证的信号。

规则可能在周末生效，因此观察日期可以覆盖下一 ISO 周的周一至周日。没有可靠依据时输出空数组，不补写“持续关注”等泛化建议。

## 10. 处理流程

```text
计算本周工作日、周五 16:00 截止点和 5 个业务日期
  → 检查目标周报是否已通过并已进入 manifest
  → 检查 5 份日报的 manifest、本地 JSON、gate 和公网文件
  → 缺失日报按原业务日期补跑；无法补齐则停止
  → 周五 16:00 执行截止增量采集；有新增则刷新周五日报
  → 合并 5 份日报 articleId
  → 回 DuckDB 补齐分析、证据和冲突
  → 执行周度跨日聚类
  → 生成候选集统计
  → 主 Agent 选择重点展示集并生成周报叙事
  → 程序校验所有 articleId、日期、数量和引用
  → Pydantic/JSON Schema 校验草稿
  → 主 Agent 执行整份报告最终关门
  → 合并 gate 后再次进行完整合同校验
  → 写入 DuckDB reports
  → 原子导出 weekly/YYYY-Www.json
  → 上传周报 JSON 并验证
  → 最后原子更新 manifest.json
  → 从公网再次验证周报与 manifest
```

## 11. 输出合同

周报 JSON 继续沿用当前报告 Schema，技术字段由程序生成和校验。页面只消费必要的展示字段，不直接暴露内部 ISO 周和构建信息。

页面真正关心的只有：

- 归档日期 `date`，固定为该周周一。
- 日期范围 `period.startDate ～ period.endDate`，固定为周一至周五。
- 数据截止 `windowEnd`，固定为周五 `16:00:00+08:00`。
- 周报标题 `lead.title`。
- 周报主线 `lead.summary`。
- 本周主题、重点资讯、重要变化、重复信号和下周关注。
- 信源目录。

归档列表不读取或展示 `period.isoWeek`、`windowStart`、`windowEnd`、`build` 等技术字段。它使用 manifest 中的 `date` 和 `title`，按周一日期在当月的位置计算归档周序；报告正文从周报 JSON 的 `period.startDate` 和 `period.endDate` 生成日期范围：

```text
2026 年 7 月
第3周    周报标题

2026-07-20 ～ 2026-07-24
```

`stats.uniqueEvents` 统计候选集跨日去重后的事件数，`stats.dailyReports` 必须等于 5；`sections` 只包含重点展示集，`sourceDirectory.articleCount` 统计最终进入 `sections` 的文章数。

新生成的 `1.2.0` 周报还必须满足 `build.dataCutoffAt = windowEnd`，并且 `generatedAt`、`gate.validatedAt` 均不得早于周五 16:00。历史 `1.1.0` 周报继续按原周六零点窗口读取。

十个固定分类即使为空也必须保留：

1. Amazon 官方政策与卖家公告
2. FBA、仓储、配送与退货
3. 平台费用、利润、税务与关税
4. 广告与流量
5. Listing、SEO、评论与 VOC
6. 账号健康、合规与知识产权
7. 跨境物流、供应链与海关
8. 竞品平台动态
9. AI 工具与运营自动化
10. 卖家社区与异常信号

## 12. 最终关门验证

### 12.1 必须拒绝的情况

- 目标不是已经到达周五 16:00 截止点的本周或显式指定的历史工作周。
- 目标日报日期不是周一至周五。
- 5 份日报没有全部通过发布完整性检查。
- 周报引用了不属于 5 份日报的 articleId。
- 候选 articleId 无法从 DuckDB 还原证据。
- 跨日重复事件在 `sections` 中重复展示。
- 5 份日报候选集中存在非空分类，但周报对应 `sections` 分类为空。
- `themes` 少于 3 个或多于 8 个。
- `themes`、`recurringSignals`、`importantChanges`、`nextWeekWatchlist` 引用了不存在于最终展示集的 articleId。
- `recurringSignals` 没有覆盖至少两个不同工作日。
- 政策、费用、生效日或截止日无法由证据支持。
- 把社区信号或单一媒体消息表述成官方确认事实。
- 重点展示事件超过上限但没有提炼。
- `sourceUrl` 或证据链接缺失。
- `sourceDirectory` 未覆盖 5 份日报的信源目录并集。
- Schema 校验失败。
- `gate.status = "passed"` 但 `gate.issues` 非空。
- 抓取链路存在未解释的全源失败、零发现或日报窗口缺口。
- 没有执行周五 16:00 截止增量采集，或发现新增后没有刷新周五日报。
- `generatedAt`、`gate.validatedAt` 早于 `windowEnd`。

### 12.2 通过条件

- 5 个目标业务日期全部有有效日报。
- 候选集只来自 5 份已发布日报。
- 全部候选文章都能从 DuckDB 回查完整证据。
- 跨日聚类、候选统计和最终展示 articleId 可复现。
- 5 份日报中每个非空分类在周报对应 `sections` 中至少保留 1 个真实候选事件。
- 所有叙事字段引用均存在于最终展示集。
- 周报通过 Pydantic/JSON Schema 校验。
- 主 Agent 返回 `gate.status = "passed"` 且 `issues = []`。
- 周五截止增量已进入周五日报，且报告在 16:00 后重新生成。
- 合并 gate 后再次通过完整合同校验。

被拒绝的周报保留草稿、覆盖诊断和关门问题，但不得导出、不得上传、不得修改 manifest。

## 13. 存储、修订与幂等

周报继续写入现有 `reports` 表，不新增周报专表。

建议标识：

- `run_id`：`weekly-YYYY-Www-rN`
- `report_id`：`weekly-YYYY-Www-rN`
- `report_type`：`weekly`
- `business_date`：该周周一
- `revision`：从 1 递增

同一 ISO 周重复执行时：

- 如果本地周报、manifest 和公网周报均已存在，且 gate、哈希和 URL 一致，则视为已完成，不重复生成或发布。
- 已通过版本不被静默改写。
- 日报内容、证据、周报 Prompt 或 Schema 发生变化时生成新 revision。
- 新 revision 通过关门后，才原子替换稳定路径 `weekly/YYYY-Www.json`。
- 远端 manifest 保存最新公开 revision。
- 数据库写入继续由单连接串行完成。

## 14. Manifest 合同

周报 manifest 条目至少包含：

```json
{
  "date": "2026-07-20",
  "title": "本周具体事件或主题标题",
  "url": "/wp-content/uploads/ecom-market-pulse/v1/weekly/2026-W30.json"
}
```

更新规则：

- 保留现有 `reports.daily`、`reports.weekly`、`reports.monthly`。
- 只新增或替换目标周的 weekly 条目。
- 三类数组都按最新日期在前。
- 只列出 `gate.status = "passed"` 且 `issues = []` 的报告。
- `date` 使用周一日期，页面据此计算月份和“第 N 周”。
- `title` 直接显示在“第 N 周”右侧。
- manifest 中不得出现 `latest.json`、临时文件或本地绝对路径。

## 15. 导出与公开发布

本地正式路径：

```text
runtime/exports/weekly/YYYY-Www.json
```

远端固定路径：

```text
/usr/local/lighthouse/softwares/wordpress/wp-content/uploads/ecom-market-pulse/v1/weekly/YYYY-Www.json
```

公网路径：

```text
https://www.woyaofei.cn/wp-content/uploads/ecom-market-pulse/v1/weekly/YYYY-Www.json
```

发布实现必须读取本机 `.env` 中的 `ECOM_MARKET_PULSE_PUBLISH_*` 约束，并执行：

1. 校验报告类型在 `daily,weekly,monthly` 白名单中。
2. 校验周报文件名符合 `YYYY-Www.json`。
3. 校验 `gate.status = "passed"` 且 `issues = []`。
4. 校验目标位于固定 `weekly` 一级目录，不创建日期子目录。
5. 拒绝上传 DuckDB、原文、日志、缓存、密钥、LLM 审计和附件。
6. 先上传周报临时文件。
7. 服务端校验 JSON、文件权限 `644` 和 SHA-256。
8. 原子替换正式周报文件。
9. 验证公网 HTTP 200 和本地/远端/公网内容一致。
10. 生成保留其他报告类型的 manifest。
11. 最后原子替换远端 `manifest.json`。
12. 再次从公网验证 manifest 中的周报 URL、标题和日期。

目录权限固定为 `755`，JSON 文件权限固定为 `644`。

## 16. 博客页面配套

`theme-document` 的跨境资讯页面已经能够读取 `reports.weekly`、`themes`、`sections`、`keyDates` 和 `nextWeekWatchlist`。

周报正式上线前还需补齐：

- 归档按 `date` 的月份分组。
- 月份标题右侧显示该月周报数量。
- 每期只显示“第 N 周 + 周报标题”。
- “第 N 周”由周一日期在当月的位置计算。
- 当前选中的周报使用整行浅色背景突出。
- 不在归档中显示 ISO 周、起止日期和时间窗口。
- 展示 `importantChanges`。
- 展示 `recurringSignals`。
- 周报主题能够定位到引用的周报事件。
- 拉取报告后验证 `report.reportType === "weekly"`。
- 拉取报告后验证 `report.gate.status === "passed"` 且 `issues` 为空。
- 继续使用 `sourceDirectory` 动态渲染信源，不在页面硬编码名单。

页面只负责消费和展示 JSON，不负责判断周报应包含哪些文章。

## 17. 调度方案

推荐使用 Codex Scheduled 在每周五北京时间 16:00 触发：

```text
执行本周跨境资讯周报完整流程。
业务时区固定为 Asia/Shanghai，目标周期为本周周一至周五，
业务截止点为周五 16:00，预期存在 5 份已发布日报。

先检查 runtime/exports/weekly/YYYY-Www.json 是否已经存在、
gate.status=passed、issues=[]，并且 manifest 与公网文件一致；
若已完整发布，不重复执行。

先执行周五截止增量采集，覆盖上午日报之后至 16:00 的新增资讯；
有新增时必须完成分析并重建周五日报。然后检查目标周 5 份日报：
每份必须存在于 manifest、本地 JSON 日期匹配、gate.status=passed、
issues=[]，且公网文件可访问并与本地一致。
缺失日报必须按对应业务日期执行完整日报补跑，不得使用其他日期、
latest.json 或历史日报替代；无法补齐 5 份日报时停止并拒绝周报。

基于刷新后的 5 份日报 articleId 构建候选集，回 DuckDB 补齐证据，
完成跨日事件聚类和重点提炼，生成主线、主题、重要变化、
重复信号和下周观察。所有引用必须属于周报最终展示集。

只有最终 gate.status=passed 且 issues=[] 的
weekly/YYYY-Www.json 才允许发布。报告先上传并完成哈希、
权限和公网校验，manifest.json 必须最后原子更新。

完成后必须报告同月归档周序“第X周”、
period.startDate ～ period.endDate 的周一至周五日期范围，
以及“数据截至周五 16:00”。
```

## 18. 实施步骤

### 第一阶段：周报编排、截止补采与 5 日覆盖

- 增加本周、周五 16:00 截止点和 5 个业务日期计算。
- 增加周五截止增量采集与当日日报刷新。
- 增加 manifest、本地日报、公网日报三方检查。
- 增加缺失日期清单和补跑入口。
- 从 5 份日报提取 articleId。
- 按 articleId 回查 DuckDB。
- 合并 5 份日报的信源目录快照。

### 第二阶段：跨日提炼

- 增加周度跨日聚类。
- 区分重复报道、后续进展和多日信号。
- 增加候选集与重点展示集。
- 为周报增加独立 `weekly-report-v1` Prompt。
- 让 Agent 输出所有周报叙事字段和重点展示 articleId。

### 第三阶段：合同与关门

- 校验全部叙事字段的 articleId 引用。
- 校验 `dailyReports = 5`。
- 校验 `dataCutoffAt = windowEnd` 和关门时间不早于周五 16:00。
- 校验重复信号覆盖至少两个工作日。
- 校验 `passed` 与空 issues 的一致性。
- 合并 gate 后再次执行完整 Schema 校验。
- 修正 `dataCutoffAt`、revision 和 reportId 语义。

### 第四阶段：发布与博客展示

- 实现 `.env` 发布白名单。
- 实现 manifest 合并和原子更新。
- 实现本地、服务端、公网三方哈希校验。
- 在博客页面展示重要变化和重复信号。
- 增加页面 reportType 和 gate 防御校验。

### 第五阶段：历史演练

至少选择一个确实拥有周一至周五 5 份已发布日报的历史工作周演练，验证：

- 5/5 日报覆盖。
- 缺失日报时拒绝周报。
- 周六、周日无日报不报错。
- 跨月、跨年 ISO 周。
- 跨日同事件去重。
- 同事件后续进展保留。
- 重复信号至少覆盖两个日期。
- 重点展示数量限制。
- 非法 articleId 引用被拒绝。
- `passed + 非空 issues` 被拒绝。
- 同一周新 revision 原子替换。
- manifest 保留日报和月报。
- WordPress 页面能加载并完整展示周报字段。

## 19. 验收标准

满足以下条件视为周报能力可用：

- 能由 Codex Skill 在周五 16:00 截止补采后生成本周周一至周五周报。
- 只依赖 5 份已发布、日期匹配、关门通过的日报。
- 周六和周日不要求日报。
- 任一目标工作日日报缺失时不会静默生成残缺周报。
- 候选集 articleId 均可从 DuckDB 还原证据。
- 能识别跨日重复报道、后续进展和重复信号。
- 周报正文是重点提炼，不是 5 份日报全文拼接。
- 日报候选集中所有非空分类在周报中均有至少 1 个代表事件，分类覆盖缺口会触发关门拒绝。
- 全部主题、变化、信号和观察项引用合法。
- `stats.dailyReports = 5`。
- `windowEnd = 周五 16:00:00+08:00`，且生成、关门时间不早于截止点。
- JSON 通过当前报告 Schema。
- 只有 `gate.status = "passed"` 且 `issues = []` 的报告可以导出和发布。
- 文件名稳定为 `weekly/YYYY-Www.json`。
- 发布严格执行报告先上传、manifest 最后更新。
- 博客页面能够展示主题、重要变化、重复信号、重点事件和下周观察。
- DuckDB 中可以还原目标日报、候选集合、周度聚类、Agent 输出、关门结论和最终 revision。

## 20. 月报复用边界

月报沿用相同业务截止原则：

- 按自然月归档，业务截止点固定为月末最后一个自然日 16:00。
- 预期日报只计算该月周一至周五。
- 周六、周日不要求日报。
- 候选集来自该月全部已发布日报与月末截止增量事实，而不是只聚合周报。
- 回 DuckDB 补齐证据后再做月度聚类和提炼。
- 任一预期工作日日报缺失时不得静默生成残缺月报。
- 顶层 `date` 固定为月初；`period.month/startDate/endDate` 构成自然月归档，`windowEnd` 为月末 16:00。
- `stats.dailyReports` 必须等于目标月周一至周五总数；第一版不处理法定节假日和调休。
- 月末 16:00 截止补采后必须重新生成，`generatedAt`、`gate.validatedAt` 均不得早于 `windowEnd`。
- 文件名固定为 `monthly/YYYY-MM.json`。
- 报告先上传，manifest 最后更新。

不建议只基于周报生成月报，否则会在已经提炼过的内容上再次提炼，造成证据和事件遗漏。

- 将 Markdown 作为唯一正式输出。
- 绕过 Codex 主 Agent 直接通过脚本发布。
